# 家庭健康管理 App 产品方案（v1.0）

> 本文档不包含页面设计与数据库表结构，这些内容在后续设计/技术文档中展开。

---

## 1. 产品定位

家庭内部使用的**健康记录与协作工具**：长期记录并共同查看家庭成员的检查、用药、日常测量信息。

### 1.1 两个核心价值（优先级并列）

1. **日常不漏**：服药不忘、测量不忘——以"提醒"为核心手段（不做打卡）。
2. **历史可溯**：复查资料不丢、跨时间的指标对比、用药变化清晰——以"结构化指标 + 事件归档"为核心手段。

### 1.2 产品边界（红线，不可突破）

- 不做医学判断：不标红、不画箭头、不提示"偏高/偏低/异常"。
- 不生成任何治疗/健康/用药建议，不做疾病分级、风险预测、紧急预警。
- 报告上的参考区间**原样存档展示**（属"忠实存档"），App 自身不做任何基于参考区间的解读。
- 不替代医生，不指导用户自行调药。
- 不以建立完整电子病历/医院系统为目标；只保留理解历史所必需的最少背景（事件备注）。
- 优先简单、清楚、可长期使用。

### 1.3 已否决项（及原因）

| 否决项 | 原因 |
|---|---|
| 服药打卡 / 漏服上报 | 高频负担，家庭坚持不下来；漏服上报接近"预警"，越界 |
| 家庭内角色权限（管理员/查看者） | 家庭默认信任，权限体系是开发量放大器；仅做录入署名 |
| 全量指标自动归并 | 跨医院指标名归一工程量大；任意指标可按原文名下钻看历史，别名归并只在重点清单内做 |
| 中药结构化（拆单味药） | 录入成本极高；自由文本足够回答"那段时间在吃什么" |
| App 内置 OCR/AI 解析（一期） | 外部强模型 + 人工验证更可靠；一期以文本导入为入口，内置解析列二期 |
| 一个账号加入多个家庭（一期） | 暂不出现该场景；账号-家庭按单一家庭归属设计，预留扩展 |
| 通用家庭备忘/待办 | 范围蔓延；仅保留健康相关提醒 |

## 2. 角色与关系模型

三个概念严格分离：

- **设备身份（用户）**：无账号登录体系。每台手机首次使用输入**家庭口令**并完成署名，此后该设备的操作自动携带署名。
- **家庭**：一个协作组。一期内一台设备属于一个家庭；组内人人可做一切操作，仅记录"谁录入"作署名（审计与追溯用途，非权限）。
- **成员档案（被记录者）**：数据归属的主体。如爷爷、奶奶；也可以是使用者本人。成员档案由家人创建，本人可以从不使用 App。

**展示逻辑**：App 内任意时刻以"当前选中的成员档案"为数据主体，可切换；所有记录、趋势、事件、用药均按人隔离。

**署名**：所有录入行为记录"创建人 + 来源（App 手动 / API 导入）"。

## 3. 核心业务循环

慢病家庭管理是一个闭环，产品围绕整个环设计：

```
日常测量 → 持续服药 → 到期复查 → 医生看结果调药 → 新用药方案 → 回到日常测量
```

- **复查事件是环的枢纽**：报告归档、指标入库、用药调整、下次复查提醒都挂在它上面。
- **数据分两类，绝不混排**：
  - 流水类（测量记录）：高频、低单条价值，走快捷录入 + 趋势视图；
  - 事件类（复查、用药变化）：低频、高价值，走时间轴。
- 成员主视图概念：**顶部状态卡（当前用药方案 + 今日提醒）+ 统一事件时间轴（复查事件、用药变化）**；测量数据不进时间轴。

## 4. 功能模块（信息架构层面，非页面设计）

一期包含以下模块：

1. **家庭与设备**：家庭口令接入、设备署名管理、成员档案管理（姓名/关系/性别/出生日期 + 自由文本静态信息，如确诊疾病、过敏史等由家人自行书写，不设固定字段）。
2. **日常测量**：血压（收缩/舒张，心率可选附属）、血糖（数值 + 测量场景：空腹/餐前/餐后/睡前/随机）的快捷录入；按周期翻页的日志表式密集查看（血压日行、血糖场景网格）+ 趋势视图。
3. **复查事件**：事件容器（日期、医院/科室、备注、下次复查日期）→ 内含多份检查报告 → 报告含结构化指标与描述性文本，照片附件归档（可下载，不做主视图）。
4. **指标对比**：两层——①任意指标可在报告内下钻查看历次数值（按原文名匹配成线）；②每人维护一份**重点指标清单**，做跨院别名归并与多指标仪表盘。
5. **用药**：两层——①方案（档案层）：当前方案（未结束的长期条目，含中西药与详细用法）+ 历史用药（按变化点分段，段内分西药/中药，段头为变化事由与关联复查）；②今日用药（执行层）：自由填写的每日服药单，西药显示余量与可服天数（余量 ÷ 每日用量），中药记剩余副数与服用进度；与方案可不一致。
6. **提醒**：服药 / 测量 / 复查三类 + 便签提醒（便签自带提醒时刻，可指定目标设备，即"提醒其他家庭成员"）；均为各设备本地通知触达，三类系统提醒全员可达，便签提醒默认全员、可指定设备。
7. **文本导入**：App 内粘贴结构化文本 → 解析 → 预览确认 → 入库；同步提供**带鉴权的 HTTP 录入接口**（一期）。
8. **导出备份**：全量数据导出（成员维度，结构化数据 + 附件打包）。

二期（明确延期）：App 内置 AI 解析报告照片、更多测量类型、多家庭归属。（原二期"家人互相提醒 nudge"已由便签提醒覆盖，从清单取消。）

## 5. 数据概念模型（实体与关键规则）

> 实体级描述，用于统一认知与指导后续的表结构与 API 设计。

### 5.1 实体清单

| 实体 | 说明 | 关键属性（概念） |
|---|---|---|
| 家庭 Family | 协作组 | 名称 |
| 账号 Account | 登录主体 | 登录凭证、所属家庭 |
| 成员档案 Profile | 被记录主体 | 姓名、与家庭关系、性别、出生日期、自由文本档案说明 |
| 测量记录 Measurement | 日常流水 | 类型（血压/血糖/心率）、数值组合、血糖测量场景、测量时间、备注、记录人 |
| 复查事件 CheckupEvent | 事件容器 | 复查日期、医院/科室（自由文本）、备注、下次复查日期、记录人 |
| 检查报告 Report | 属于复查事件 | 报告标题/类型、检查日期、描述性结论文本、来源、记录人 |
| 指标项目 IndicatorItem | 属于报告 | 项目名称（原文）、数值或定性结果（阳性/阴性等）、单位（原文）、参考区间（原文） |
| 重点指标 WatchItem | 属于成员档案 | 标准名、别名列表（跨医院名称归一）、对比用标准单位与换算规则 |
| 用药条目 MedicationItem | 有生命周期 | 分类（长期/临时）、中西药、名称、用法用量（文本，中药写详细）、服用时段（可空）、开始/结束时间、改量链、所属变化、记录人 |
| 用药变化 MedChange | 一次用药调整的批次 | 生效日期、事由（自由文本）、关联复查事件（可空）、记录人 |
| 今日用药 DailyMedItem | 家庭实际执行的服药单，与方案可不一致 | 西药：名称、每次用量、时段、余量、每日用量；中药：剩余副数、每副天数、已吃天数；记录人 |
| 提醒 Reminder | 到点本地通知 | 类型（服药/测量/复查）、关联对象、时间规则、目标成员档案 |
| 便签 Note | 家庭便签/待办，多条并存 | 文本、完成标记、提醒时刻（可空）、目标设备（可空=全员）、记录人 |
| 附件 Attachment | 归档照片 | 关联报告、压缩存储、可下载 |

### 5.2 关键规则

1. **结束不删除**：停药 = 写结束时间，条目永留历史。
2. **改量 = 旧条目结束 + 新条目开始**：保证"新信息不覆盖旧记录"在模型层成立。
3. **用药变化成批记录**：一次"记用药变化"产生一条 med_changes（生效日期 + 事由 + 关联复查），批次内的条目增停改以 change_id 归属；历史按变化点分段展示，段头即批次事由，复查事件与用药变化双向可追溯。
4. **临时用药隔离**：出现在历史用药分段（还原"那段时间在吃什么"），但不进入"当前方案"卡片与服药提醒——否则每次感冒都要打断长期提醒逻辑。
5. **指标归一只在重点清单内做**：录入保留医院原文名称；对比时通过别名映射到标准名；单位不一致时在清单内配置换算。
6. **定性指标与定量指标并存**：尿常规等含"阳性/阴性/+"类结果，指标模型必须同时支持数值与文本结果。
7. **描述性结论单独承载**：B 超/CT 的"所见/提示"为报告级自由文本，不强行字段化。
8. **便签提醒自驱动**：不建 reminders 行，notes.remind_at 同步后由各设备本地调度，仅目标设备触发，无需远程推送。

## 6. 导入通道与数据质量

一期录入主路径（复查数据）：

```
报告原件 → 外部 AI 整理为结构化文本 → 人工核对 → [App 粘贴导入 | HTTP API 提交] → 服务端校验 → 入库
```

- **格式**：定义带版本号的结构化文本格式（JSON），版本字段必填，便于将来演进不破坏旧客户端。
- **校验**：服务端做模式校验（结构、必填、数值合法性）；校验失败整体拒绝并返回明细，不产生半截数据。
- **幂等**：客户端每次提交生成唯一 import_id，重复提交不产生重复档案。
- **API 鉴权**：家庭维度签发 token；API 写入的记录来源标记为 api，署名到 token 对应账号。
- **预览确认**：App 粘贴导入路径必须经"解析预览 → 人工确认"再入库；HTTP 路径默认直接入库（视同事前已人工核对），但提供 dry-run 模式只校验不写库。
- **照片附件**：与报告一并归档（压缩），主视图不展示，可查看/下载原件——它是转录错误的最终纠错依据。

## 7. 提醒系统

- 三类系统提醒：**服药提醒**（由当前长期方案的用法生成每日时刻）、**测量提醒**（自定义周期）、**复查提醒**（按复查事件的"下次复查日期"提前推送）；**便签提醒**：便签自带时刻，到期触发。
- 接收策略：系统提醒**家庭全员**；便签提醒默认全员、可指定设备。全部经本地通知触达，一期不接远程推送。
- 提醒只推送，不要求打卡确认，无漏服/漏测判定与上报。
- 用药条目结束或调整时，关联提醒随之更新/停止（由"当前方案"自动推导，不需手动维护提醒清单）。

## 8. 关键场景走查（验证模型完备性）

1. **复查日**：复查前一晚收到提醒 → 当天检查 → 回家拍照归档 + 外部 AI 整理文本 → 粘贴导入 → 预览确认 → 报告入库 → 若医生调药：结束/新增用药条目并关联本次复查 → 填写下次复查日期（自动生成新提醒）。✔
2. **感冒临时用药**：记一次用药变化（事由"感冒"，新增临时条目带起止时间）→ 归入历史用药分段，不动当前方案与服药提醒。✔
3. **看病取证**：医生问"上次 ACR 多少"→ 切到爷爷 → 重点指标对比 → 10 秒内答出；医生要看原件 → 打开报告附件下载/展示。✔
4. **回溯历史**："去年这阶段吃什么药"→ 时间轴滑动到对应区间 → 当时进行中的条目与变化节点清晰可见。✔
5. **日常**：爸爸到点收到全家推送 → 提醒爷爷吃药/测压 → 30 秒内录入血压。✔

## 9. 非功能与成本考虑（技术阶段展开，先立原则）

- **成本大头是照片存储**：压缩 + 冷归档策略；同步与文本数据成本极低。
- **Android 推送**：国内环境需考虑厂商通道或第三方推送服务，是提醒可靠性的关键风险点，技术选型阶段专项评估。
- **隐私**：健康数据敏感；HTTP 接口与导出功能要求鉴权与传输加密；外部 AI 处理报告文本属于用户自主行为，但产品文档中应提示隐去姓名等敏感信息后再喂给外部模型。
- **导出备份**：结构化数据（JSON）+ 附件打包，按成员维度导出；防止锁定焦虑，也是服务不可用时用户的退路。
