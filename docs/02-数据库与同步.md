# 数据库表结构与同步策略（v1.0）

> 依据 `01-产品方案.md` 第 5 节概念模型落地。本文档与技术栈无关，字段类型为逻辑类型，最终物理类型随技术选型微调。

---

## 1. 设计前提与关键决策

| 决策 | 结论 | 理由 |
|---|---|---|
| 权威数据源 | **服务端为权威**，App 本地只读缓存，支持离线查看 | 家庭场景几乎始终在线；避免离线写带来的冲突复杂度 |
| 写入方式 | 在线写入，失败进入本地重试队列 | 录入动作轻，重试成本低 |
| 主键 | **UUID，客户端可生成** | 天然幂等；API 导入与 App 写入统一；为将来离线写预留可能 |
| 删除 | 一律软删除（tombstone），不同步物理删除 | 健康数据不允许误删即毁；同步需要墓碑 |
| 冲突策略 | 追加型表（测量/报告/指标）天然无冲突；可改表（档案/用药/提醒）**服务端时钟 LWW** | 家庭协作冲突概率极低，LWW 足够且简单 |
| 变更追踪 | 每行携带服务端递增序号 `seq` | 增量同步的唯一依据（见第 4 节） |
| 时间存储 | 时刻用 UTC epoch 毫秒 + 时区偏移；纯日历日期（复查日、起止日期）用 ISO `YYYY-MM-DD` 不带时区 | 避免跨时区旅行/换机导致日期漂移 |

## 2. 通用列（所有业务表）

| 列 | 类型 | 说明 |
|---|---|---|
| id | uuid | 主键，客户端/API 生成 |
| family_id | uuid | 冗余于所有表，隔离与查询的最小边界 |
| created_by | uuid | 设备 id，署名（见 3.2） |
| source | enum(`app`,`api`) | 录入来源 |
| created_at / updated_at | int64 epoch ms | 服务端时钟 |
| deleted | bool | 软删除墓碑 |
| seq | int64 | 服务端全局递增，每次写入/更新/删除时刷新 |

索引通则：`seq` 单列索引（增量同步）；`family_id` 参与所有业务查询的联合索引。

## 3. 表定义

### 3.1 families 家庭
| 列 | 类型 | 说明 |
|---|---|---|
| id | uuid | |
| name | text | 家庭名称 |

### 3.2 devices 设备（设备即身份，无账号体系）
| 列 | 类型 | 说明 |
|---|---|---|
| id | uuid | |
| family_id | uuid | 一期一台设备仅属一个家庭；多家庭需加关联表，已列为演进风险 |
| type | enum(`member`,`api`) | member=家人手机；api=HTTP 导入令牌 |
| display_name | text | 署名展示用（"爸爸"）；type=api 时为令牌备注名 |
| token_hash | text | 设备令牌哈希（首次以家庭口令换取；原文不落库） |
| revoked_at | int64 可空 | 吊销时间；家庭口令更换后全部失效 |
| last_seen_at | int64 可空 | 最近活跃，辅助管理 |

### 3.3 profiles 成员档案
| 列 | 类型 | 说明 |
|---|---|---|
| id | uuid | |
| name | text | |
| relation | text | 与家庭关系（自由文本："爷爷"） |
| gender | enum(`male`,`female`,`unknown`) | |
| birth_date | date | 可空，用于报告展示年龄 |
| notes | text | 自由文本静态档案（确诊疾病、过敏史等），不设结构字段 |
| linked_device_id | uuid 可空 | 若档案主体本人也使用 App（爸爸），关联其设备 |

### 3.4 measurements 测量记录（追加型）
| 列 | 类型 | 说明 |
|---|---|---|
| id, profile_id | uuid | |
| type | enum(`bp`,`glucose`) | 心率不单列类型 |
| measured_at | int64 + tz_offset_min(int) | 测量时刻 |
| systolic / diastolic | int 可空 | type=bp |
| heart_rate_bpm | int 可空 | type=bp 时可选（脉搏附属项） |
| glucose_mmol | numeric(5,2) 可空 | type=glucose |
| glucose_context | enum(`fasting`,`before_meal`,`after_meal_2h`,`bedtime`,`random`) 可空 | 血糖必填场景 |
| note | text 可空 | |
| payload | jsonb | 预留：二期新测量类型不落新表，先进 payload；一期概览时间分段只由 measured_at 推导，不在 payload 重复存时段 |

索引：`(family_id, profile_id, type, measured_at desc)`

### 3.5 checkup_events 复查事件
| 列 | 类型 | 说明 |
|---|---|---|
| id, profile_id | uuid | |
| checkup_date | date | |
| hospital / department | text 可空 | 自由文本 |
| note | text 可空 | "医生说了什么"等背景 |
| medication_changes_note | text 可空 | 本次复查相关的用药情况展示性备注（对应 03 §3 同名字段） |
| next_checkup_date | date 可空 | 驱动复查提醒 |

索引：`(family_id, profile_id, checkup_date desc)`

### 3.6 reports 检查报告
| 列 | 类型 | 说明 |
|---|---|---|
| id, event_id | uuid | 必须属于某复查事件 |
| title | text | 报告名（"尿常规"） |
| report_date | date | 可与事件日不同（如活检延迟出报告） |
| conclusion_text | text 可空 | 描述性结论（B 超"所见/提示"），不字段化 |

### 3.7 indicator_items 指标项目（追加型）
| 列 | 类型 | 说明 |
|---|---|---|
| id, report_id | uuid | |
| item_name | text | 医院原文名称，**不做归一改写** |
| value_numeric | numeric 可空 | 定量值 |
| value_text | text 可空 | 定性值（"阴性"、"+"）；与 value_numeric 二选一必填 |
| unit | text 可空 | 原文单位 |
| reference_range | text 可空 | 原文参考区间，仅存档展示 |
| sort_order | int | 保持报告原始排列 |

### 3.8 watch_items 重点指标清单
| 列 | 类型 | 说明 |
|---|---|---|
| id, profile_id | uuid | 每人一份 |
| canonical_name | text | 标准名（"ACR"） |
| aliases | jsonb text[] | 别名归一（["尿微量白蛋白/肌酐比","ACR(尿)"]） |
| canonical_unit | text 可空 | 对比统一单位 |
| unit_factors | jsonb 可空 | `{原文单位: 换算系数}`，跨医院单位换算 |
| sort_order | int | |

匹配规则：录入指标落入对比 = `item_name ∈ aliases`（精确匹配，服务端在写入时预解析出 `canonical_name` 冗余存储到 indicator_items 上，避免对比时逐次匹配；别名变更后批量重刷）。

下钻规则（05 文档 4.1）：**任意指标**都可按 `item_name` 精确匹配拉出历次历史（同院同名自然成线）；watch_items 的别名归并同时作用于下钻，使跨院不同名指标不断档。清单不是查看资格，而是归并与仪表盘的配置。

### 3.9 medication_items 用药条目
| 列 | 类型 | 说明 |
|---|---|---|
| id, profile_id | uuid | |
| category | enum(`long_term`,`temporary`) | |
| med_kind | enum(`western`,`tcm`) | 西药/中药，默认 `western`；历史用药按此分组展示 |
| name | text | 药品名或中药方描述 |
| dosage_text | text | 中药详细用法与旧版西药自由文本；结构化西药不依赖解析此字段 |
| dose_qty | numeric 可空 | 西药每个服用时段的一次用量，支持半片等小数 |
| dose_unit | text 可空 | 西药剂量单位，默认“片”；库存与剂量必须同单位 |
| dose_times_per_day | smallint 可空 | 西药明确填写的一天次数；结构化用量存在时须为 1–4，且等于 dose_slots 数量 |
| dose_slots | jsonb text[] 可空 | 服用时段子集：`["morning","noon","evening","bedtime"]` |
| start_date | date | |
| end_date | date 可空 | NULL = 进行中 |
| supersedes_id | uuid 可空 | 改量链条：本条目替代了哪条旧条目 |
| change_id | uuid 可空 | 产生本条目的用药变化（见 3.10） |

**当前方案** = `profile_id=? AND category='long_term' AND end_date IS NULL AND deleted=false`。
**改量** = 旧条目写 end_date + 新条目 supersedes_id 指向旧条目；**停用** = 仅写 end_date。
事由与关联复查由 med_changes 承载，条目不重复记录；当前方案卡片不显示余量与日期。
索引：`(family_id, profile_id, category, end_date)`

### 3.10 med_changes 用药变化（一次调整的批次）
| 列 | 类型 | 说明 |
|---|---|---|
| id, profile_id | uuid | |
| effective_date | date | 生效日期，历史用药分段的边界点 |
| note | text 可空 | 事由，自由文本（"复查后调整"、"感冒"） |
| linked_event_id | uuid 可空 | 关联触发本次变化的复查事件 |

一次"记用药变化"产生一条 med_changes + 若干条目变更（新增条目以 change_id 归属）。历史用药按变化点分段，段头即此表的 note 与 linked_event_id；从复查事件与用药变化双向可追溯。

### 3.11 reminders 提醒
| 列 | 类型 | 说明 |
|---|---|---|
| id, profile_id | uuid | |
| type | enum(`medication`,`measure`,`checkup`) | |
| times | jsonb text[] | medication/measure：每日时刻 `["08:00","20:00"]` |
| measure_type | enum 可空 | type=measure 时区分血压/血糖 |
| advance_days | jsonb int[] | type=checkup：提前天数 `[7,1,0]`，默认 `[1]` |
| enabled | bool | |

设计决策：**服药提醒是"档案级时刻表"，不与单条用药绑定**。通知触发时动态拼当前方案内容。西药每日次数由用户明确填写并保存为 `dose_times_per_day`，提交时必须与 `dose_slots` 数量一致；药格扣减仍以具体时段为准。用药变动时无需重建提醒，满足"提醒随方案自动更新"。

注：便签提醒不在此表，由 notes.remind_at 自驱动（见 3.14）。

### 3.12 attachments 附件
| 列 | 类型 | 说明 |
|---|---|---|
| id | uuid | |
| report_id | uuid 可空 | 附件先于报告上传（02 §4.4），归属在导入事务内回填 |
| file_key | text | 存储路径 |
| mime / size_bytes / sha256 | - | 完整性校验 |
| upload_state | enum(`pending`,`done`) | 断点续传与清理依据 |

### 3.13 api_tokens（已并入 devices）
HTTP 导入令牌即 `type=api` 的 devices 行：token_hash 鉴权、display_name 作备注、created_by 即署名、revoked_at 吊销。不再单设表。

### 3.14 notes 便签
| 列 | 类型 | 说明 |
|---|---|---|
| id, profile_id | uuid | 属于成员档案，**多条并存** |
| text | text ≤500 | 便签内容（"爷爷这周感冒，注意观察"） |
| done | bool | 作为待办时可勾选完成 |
| remind_at | int64 + tz_offset_min(int)，可空 | 可空 = 不提醒 |
| remind_targets | jsonb uuid[] 可空 | 目标设备 id 列表；NULL = 全家设备 |

设计决策：便签提醒**不建 reminders 行**——notes.remind_at 自驱动，各设备同步后本地调度，仅 remind_targets 命中的设备触发（对应"提醒其他家庭成员"），全程无需远程推送。索引：`(family_id, profile_id, created_at desc)`。

### 3.15 daily_med_items 今日用药清单（执行层）
| 列 | 类型 | 说明 |
|---|---|---|
| id, profile_id | uuid | |
| medication_item_id | uuid | 关联当前用药条目；同一档案内唯一，不复制药名、剂量或时段 |
| stock_by_slot | jsonb object | 各药格在盘点时的实际余量，如 `{"morning":12,"noon":12,"evening":12}`；键必须属于关联条目的 dose_slots，值非负 |
| stock_counted_at | int64 + tz_offset_min(int) | 本次实际盘点时刻；用于从盘点量推算此后各时段理论消耗 |

设计决策：本表是**当前方案的药盒库存执行层**。药名、每次用量、单位和服用时段一律从 `medication_items` 读取；预计剩余、完整可服天数与最早补药时点属于随时间变化的派生结果，不落库。多设备只同步盘点事实，由各端按相同规则计算。

四时段采用“最晚服用时间”扣减：早 `11:59`、中 `17:30`、晚 `20:30`、睡前 `23:59`；超过对应截止时刻后，理论余量扣除关联药品的一次用量。各时段独立计算，不能用总库存除以每日总量替代。改量生成新 medication_items 行时，daily_med_items 自动迁移到新条目：先按旧剂量结算至迁移时刻，再保留各格余量、刷新盘点时刻并使用新剂量继续推算；停药后不在概览展示，库存行保留供恢复或追溯。

## 4. 同步策略

### 4.1 下行（服务端 → App，增量拉取）
- 服务端每次写入/更新/软删，该行 `seq` 刷新为全局递增值（实现：数据库序列或变更触发器统一赋值）。
- App 持久化 `last_seq`，启动与下拉时请求 `GET /sync?since={last_seq}&limit=500`，服务端按 seq 升序返回本家庭全部变更行（含墓碑），客户端逐批应用并推进 `last_seq`。
- 首次全量同步走同一接口（`since=0`），无特殊路径。
- 表识别：同步载荷为 `{table, row}` 数组，客户端按表分发到本地镜像表。

### 4.2 上行（App/API → 服务端）
- 每个变更请求携带 **客户端生成的 UUID 主键** + `Idempotency-Key` 请求头（写入批次唯一）。
- 服务端对已处理的 Idempotency-Key 直接返回首次结果，网络重试/双击不产生重复数据。
- 追加型数据（测量、报告、指标、附件元数据）只增不改，天然无冲突。

### 4.3 冲突与一致性
- 可改行（profiles、medication_items、reminders、watch_items、notes、daily_med_items、med_changes、checkup_events）：以服务端接收顺序 LWW，整行覆盖（不合并字段）。家庭场景下同档案同时编辑极罕见，不做字段级合并，避免复杂度。checkup_events 开放可改是为了"下次复查日期改期/备注修正"这一真实需求（2026-09-08 补充）。
- 客户端编辑基于稍旧数据时，服务端不做版本拒绝——因为丢失的编辑可由署名与时间轴追溯，业务上可接受。

### 4.4 附件同步
- 元数据随 4.1 增量同步；二进制**懒加载**：查看/下载时才拉取并本地缓存。
- 上传：App 端先压缩（长边约 1600px、JPEG q80），携带 UUID 与 sha256；服务端校验后 `upload_state=done`。
- 存储策略见技术选型文档（一期服务器磁盘 + 备份）。

### 4.5 提醒的同步形态
- reminders 表同步到家庭所有设备后，**由各设备自行调度本地通知**（一期不走远程推送，论证见技术选型文档）。
- 用药/测量提醒按 times 每日重复；复查提醒在同步发现 next_checkup_date 时按 advance_days 生成；便签提醒同理由 notes.remind_at 驱动，仅目标设备触发。

### 4.6 导出备份
- 按家庭或成员导出：结构化数据导出为 JSON（即同步载荷的全量形态），附件原文件打包 zip。
- 导出格式与导入格式 v1 保持同一字段命名，保证"导出物可再导入"（备份真正可用）。

## 5. 演进策略

- 数据库结构变更走迁移脚本（每次发版顺序执行），`schema_version` 记录于服务端。
- 导入格式版本（见 `03-导入格式-v1.md`）与数据库结构版本**相互独立**，格式层做兼容适配，不允许格式变更倒逼破坏性改表。
- 已知演进风险：① 设备多家庭（需 device_family 关联表）；② 新测量类型（先进 payload，稳定后再列化）；③ 远程推送接入（reminders 不变，仅增下发通道）。
